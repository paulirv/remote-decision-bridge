System Overview

Philosophy

This system follows a "solo-first, team-ready" design philosophy:

  • Solo developers get lightweight tooling that doesn't add bureaucratic overhead
  • Teams can scale up the same tooling for formal project management
  • Risk-appropriate - use more rigor for high-stakes projects, less for sandboxes

Traceability

Every entity can be traced through the system:

  • Vision sets goals and success criteria for the product
  • Product Spec defines capabilities (CAP-NN) that drive requirements
  • Requirements trace to capabilities, solutions, sprints, tests, and releases
  • Risks link to affected requirements and solutions
  • Change requests modify requirements and impact sprints
  • Incidents link back to releases and spawn action items

Phase 1.5: Vision & Product Specification

Purpose

Define why you're building this product and what it will do at a high level. This creates the foundation that drives all requirements.

The Flow


Vision (optional) ──► Product Spec (required) ──► Requirements
     │                      │                         │
     └── WHY               └── WHAT                  └── HOW MUCH
         Goals                  Capabilities (CAP-NN)     Acceptance Criteria
         Success Criteria       NFRs                      Scope
         Scope Boundaries       Constraints               Dependencies

Steps

1.5.1 Create Project Vision (Optional but Recommended)

Command: /spec vision

The vision document answers fundamental questions:

  1. What problem are we solving? - The pain point or opportunity
  2. Who is affected? - Target users and stakeholders
  3. What does success look like? - Measurable goals
  4. What's in scope? - Boundaries of the project

Claude guides you through creating a vision document with:

  • Executive summary (elevator pitch)
  • Problem statement and pain points
  • Vision statement and key goals
  • Value proposition for each stakeholder
  • Success criteria (must achieve, should achieve, could achieve)
  • Scope boundaries

File: .claude/project-management/vision.md

Template: vision.md

1.5.2 Create Product Specification (Required)

Command: /spec create

The product specification is the required foundation for all requirements. It defines:

  1. Product Overview - What this is and why it exists
  2. Users and Stakeholders - Who we're building for
  3. Capabilities (CAP-NN) - What the product must do
  4. Non-Functional Requirements - Performance, security, accessibility
  5. Constraints - Technical, business, regulatory limits
  6. Dependencies - External and internal dependencies
  7. Scope - What's in and out

Claude guides you through each section, asking clarifying questions.

Key Concept: Capabilities

Capabilities are high-level functions the product must perform. Each capability gets an ID (CAP-01, CAP-02, etc.) and drives the creation of detailed requirements.

Example capabilities:


| ID     | Capability           | Priority    | Status   |
|--------|---------------------|-------------|----------|
| CAP-01 | User Authentication | Must Have   | Proposed |
| CAP-02 | API Design          | Must Have   | Proposed |
| CAP-03 | Reporting           | Should Have | Proposed |

File: .claude/project-management/product-spec.md

Template: product-spec.md

1.5.3 Approve the Specification

Command: /spec approve

Before creating requirements, the specification should be approved. This ensures:

  • [ ] All sections complete
  • [ ] Open questions resolved
  • [ ] Stakeholders aligned
  • [ ] Scope clearly defined
  • [ ] Success metrics agreed

Status Changes:

  • draft → review → approved

1.5.4 View Capabilities

Command: /spec capabilities

Lists all capabilities and their linked requirements:


ID      | Capability           | Priority    | Requirements
--------|---------------------|-------------|---------------
CAP-01  | User Authentication | Must Have   | REQ-0001, REQ-0002
CAP-02  | API Design          | Must Have   | REQ-0003
CAP-03  | Reporting           | Should Have | (none yet)

Highlights capabilities that need requirements created.

When to Skip Vision

You can skip the vision document for:

  • Small, well-defined projects
  • Single-feature additions to existing products
  • Technical debt / refactoring efforts

The product specification is always required as the foundation for requirements.

Deliverables

  • [ ] Vision document created (optional)
  • [ ] Product specification created
  • [ ] Specification approved
  • [ ] Capabilities identified with priorities

Phase 2: Requirements & Planning

Purpose

Capture detailed requirements from the product specification, identify risks, and create the product backlog.

Requirement Lifecycle

Requirements flow through these states:


candidate ──► approved ──► draft ──► active ──► implemented ──► completed
    │             │
    └── rejected  └── deprecated
StatusMeaning
candidateProposed but NOT approved for implementation
approvedApproved for inclusion, needs detailed specification
draftBeing specified with acceptance criteria
activeReady to work on, fully specified
implementedCode complete, awaiting verification
completedAll acceptance criteria verified
rejectedNot approved for inclusion (document reason)
deprecatedWas approved but no longer relevant

Steps

2.1 Propose Requirements from Capabilities

Command: /requirement propose

For each capability in the product specification, propose one or more requirements:

  1. Link to capability (CAP-NN)
  2. Describe what needs to be built
  3. Set initial priority (must-have, should-have, could-have, won't-have)
  4. Status is set to candidate

Example Workflow:


User: /requirement propose
Claude: Which capability does this requirement address? (e.g., CAP-01)
User: CAP-01 User Authentication
Claude: What aspect of user authentication?
User: Login with email and password
Claude: [Creates REQ-0001-login as candidate]
Claude: Requirement REQ-0001 created as CANDIDATE. Use /requirement approve REQ-0001 to approve.

2.2 Approve Requirements

Command: /requirement approve <REQ-NNNN>

Review candidate requirements and approve for implementation:


User: /requirement approve REQ-0001
Claude: Any conditions or notes for approval?
User: Ensure we support Remember Me functionality
Claude: [Updates REQ-0001 to approved status with conditions]

Command: /requirement reject <REQ-NNNN>

If a requirement shouldn't proceed:


User: /requirement reject REQ-0005
Claude: Reason for rejection?
User: Deferred to phase 2
Claude: [Updates REQ-0005 to rejected status with reason]

2.3 Specify Requirements in Detail

Command: /requirement create <REQ-NNNN> or /requirement create

For approved requirements, add detailed specification:

  1. Claude asks clarifying questions
  2. Generates detailed content:
  • Summary and rationale
  • User story (As a... I want... So that...)
  • Acceptance criteria (AC-01, AC-02, etc.) - at least 3
  • Scope (in/out)
  • Dependencies
  • Non-functional requirements
  1. Status moves to draft or active based on completeness

Agent: Use requirements-analyst for help capturing complete, testable requirements.

Template: requirement.md

File: .claude/requirements/requirements/REQ-NNNN-{slug}.md

2.2 Design Solutions

Command: /solution create

For each requirement (or group of related requirements):

  1. Link to the requirement(s) being addressed
  2. Describe the proposed approach
  3. Document trade-offs and alternatives considered
  4. Get solution accepted before implementation

Agent: Use solution-architect for help designing solutions with proper trade-off analysis.

Template: solution.md

2.3 Identify Risks

Command: /risk create

For each identified risk:

  1. Describe the risk and its potential impact
  2. Assess probability (high/medium/low) and impact (critical/high/medium/low)
  3. Define mitigation strategies (prevention + contingency)
  4. Assign owner and review schedule

Command: /risk assess

Run a risk identification session to systematically identify risks across categories:

  • Technical risks
  • Schedule risks
  • Resource risks
  • External risks
  • Scope risks
  • Quality risks

Command: /risk matrix

Visualize all active risks in a probability/impact matrix:

Agent: Use risk-manager for help identifying and assessing risks.

Template: risk-register.md

2.4 Build the Backlog

Command: /backlog add

Add items to the product backlog with:

  • Description
  • Priority (must-have, should-have, could-have, won't-have)
  • Size estimate (XS, S, M, L, XL or story points)
  • Link to requirement (REQ-NNNN)

Command: /backlog list

View the backlog organized by priority.

Command: /backlog prioritize

Reorder items based on business value, dependencies, and risk.

Command: /backlog groom

Run a grooming session to:

  • Review and reprioritize top items
  • Estimate unestimated items
  • Check readiness (clear acceptance criteria, dependencies identified)
  • Add new items

File: .claude/project-management/backlog.md

2.5 Update Traceability Matrix

File: .claude/project-management/traceability-matrix.md

As requirements and solutions are created, update the RTM to show:

  • Which requirements have solutions
  • Which requirements are in sprints
  • Test coverage status
  • Release mapping

Phase 3: Sprint Execution

Purpose

Execute work in time-boxed iterations with clear goals and tracking.

Steps

3.1 Start a Sprint

Command: /sprint start

Claude guides you through:

  1. Sprint number: Auto-incremented from existing sprints
  2. Sprint name: Descriptive theme (e.g., "User Authentication")
  3. Duration: Default 2 weeks
  4. Sprint goal: 1-2 sentences describing success
  5. Capacity: Available days/hours
  6. Backlog selection: Choose items from backlog (recommend 80% capacity)

Creates SPRINT-NN.md with:

  • Sprint metadata
  • Committed items
  • Daily progress section
  • Metrics section
  • Retrospective section

Agent: Use project-manager for help with sprint planning.

Template: sprint.md

3.2 Daily Standups

Command: /standup or /standup quick

Generates a quick status update:


📍 Standup - 2026-01-21

✅ Yesterday:
- Completed login form implementation
- Made progress on password validation (70%)

🎯 Today:
- Continue password validation
- Start session management

🚧 Blockers:
- None

Sprint: 12/20 points | Day 5 of 10

Command: /standup detailed

More comprehensive update with accomplishments, focus areas, upcoming work, blockers, and notes.

Command: /standup yesterday

Review mode - what was accomplished yesterday based on git log and sprint updates.

3.3 Track Progress

Command: /sprint status

Shows current sprint progress:

  • Days elapsed/remaining
  • Points completed/committed
  • Burndown status (ahead/on-track/behind)
  • Completed items
  • In-progress items
  • Todo items
  • Blockers

Command: /sprint add <item>

Add an item to the current sprint (carefully - watch capacity).

Command: /sprint complete <item>

Mark an item as done in the current sprint.

3.4 Handle Changes

Command: /change create

When scope needs to change mid-sprint:

  1. Document the change request
  2. Analyze impact (scope, schedule, effort, cost)
  3. Consider alternatives
  4. Get approval
  5. Update sprint if approved

Agent: Use project-manager for impact analysis.

Template: change-request.md

3.5 Manage Blockers

When blocked:

  1. Document in sprint file under "Blockers & Risks"
  2. Escalate if needed (see stakeholder communication plan)
  3. Create risk if blocker indicates a pattern

Agent: Use stakeholder-liaison for help with escalation communication.

3.6 Sprint Review

Command: /sprint review

At the end of the sprint:

  1. What Was Delivered: List completed items with demo notes
  2. Incomplete Items: Document what wasn't finished and why
  3. Metrics: Calculate velocity and completion rate
  4. Stakeholder Feedback: Capture feedback from demo

3.7 Sprint Retrospective

Command: /retrospective or /retrospective standard

Classic format:

  • What went well
  • What could improve
  • Action items

Command: /retrospective start-stop-continue

Behavior-focused format:

  • Start doing (new practices)
  • Stop doing (waste elimination)
  • Continue doing (preserve what works)

Command: /retrospective 4ls

Emotional/learning format:

  • Liked (enjoyable aspects)
  • Learned (new knowledge)
  • Lacked (missing elements)
  • Longed for (wishes)

Agent: Use project-manager to facilitate retrospectives.

Phase 4: Release Management

Purpose

Package completed work and deploy to production safely.

Steps

4.1 Plan a Release

Command: /release plan

Define what's going into this release:

  1. Version: Following semver (major.minor.patch)
  2. Release type: major/minor/patch/hotfix
  3. Target date
  4. Included sprints: Which sprints are included
  5. Requirements delivered: List of completed requirements
  6. Breaking changes: Document any breaking changes

Creates REL-{version}.md in .claude/project-management/releases/

Agent: Use release-engineer for release planning.

Template: release-notes.md

4.2 Prepare for Release

Command: /release prepare

Verification checklist:

  • [ ] All planned items completed
  • [ ] Tests passing
  • [ ] Documentation updated
  • [ ] Breaking changes documented
  • [ ] Rollback plan ready

Generate release notes covering:

  • Features (from requirements)
  • Improvements
  • Bug fixes
  • Breaking changes
  • Known issues

4.3 Create Deployment Checklist

Command: /release checklist

Creates DEPLOY-REL-{version}.md with comprehensive checklist:

Pre-Deployment (Day Before):

  • Code readiness
  • Build verification
  • Staging verification
  • Documentation
  • Communication
  • Rollback preparation

Deployment Day:

  • Pre-deployment checks
  • Go/No-go decision
  • Deployment steps
  • Post-deployment monitoring

Template: deployment-checklist.md

Agent: Use release-engineer for deployment planning.

4.4 Deploy

Command: /release deploy

Interactive deployment guide:

  1. Verify all pre-deployment checks passed
  2. Confirm go/no-go decision
  3. Walk through deployment steps
  4. Run smoke tests
  5. Monitor for issues
  6. Update release status

4.5 Rollback (if needed)

Command: /release rollback

If issues are detected:

  1. Confirm rollback decision
  2. Execute rollback steps from checklist
  3. Verify rollback success
  4. Update release status to "rolled-back"
  5. Create incident postmortem

Trigger conditions for rollback:

  • Error rate exceeds threshold
  • Critical functionality broken
  • Performance significantly degraded
  • Security vulnerability discovered

Hooks Active in This Phase

HookTriggerEffect
pre-release-checklist.shBash (deploy/release)Warns if checklist incomplete

Deliverables

  • [ ] Release plan created
  • [ ] Release notes generated
  • [ ] Deployment checklist completed
  • [ ] Successful deployment (or rollback)
  • [ ] Post-deployment verification passed

Phase 5: Operations & Maintenance

Purpose

Monitor production, handle incidents, and maintain the system.

Steps

5.1 Status Reporting

Command: /status quick

Fast status snapshot for standups or quick check-ins.

Command: /status weekly

Comprehensive weekly report including:

  • Executive summary with health indicator
  • Accomplishments
  • In progress
  • Planned next week
  • Blockers and risks
  • Sprint progress
  • Release status

Command: /status monthly

Monthly summary with trends and metrics.

Agent: Use project-manager for status report preparation.

Template: status-report.md

5.2 Incident Response

When an incident occurs:

Immediate Response:

  1. Assess severity (S1-Critical to S4-Minor)
  2. Assemble response team
  3. Investigate and mitigate
  4. Communicate status to stakeholders

Post-Incident:

  1. Document timeline
  2. Conduct root cause analysis (5 Whys)
  3. Create action items
  4. Update risks if patterns emerge

Template: incident-postmortem.md

Agent: Use release-engineer for incident response and postmortem facilitation.

5.3 Risk Management

Command: /risk list

Review active risks regularly (at least bi-weekly).

Command: /risk update <RISK-NNNN>

Update risk status, reassess probability/impact, track mitigation progress.

Command: /risk matrix

Visualize current risk landscape.

Hook: risk-review-reminder.sh fires at session end if risks haven't been reviewed in 2+ weeks.

5.4 Change Control

Command: /change list

Review pending change requests.

Command: /change approve <CR-NNNN> or /change reject <CR-NNNN>

Record approval decisions.

Command: /change implement <CR-NNNN>

Track implementation of approved changes.

5.5 Quality Assurance

Review Definition of Done periodically:

  • Are quality gates being met?
  • Should criteria be added or adjusted?
  • Are escaped defects indicating gaps?

Agent: Use qa-strategist for quality process improvements.

HookTriggerEffect

session-summary-reminder.shStopPrompts for session documentation

Ongoing Deliverables

  • [ ] Weekly status reports
  • [ ] Incident postmortems (as needed)
  • [ ] Risk register updated
  • [ ] Change requests processed
  • [ ] Quality metrics tracked

When to Invoke Agents

Risk Manager - Invoke when:

  • Starting a new project phase
  • Encountering unexpected problems
  • Before major technical decisions
  • During release planning
  • Periodic risk review sessions

Project Manager - Invoke when:

  • Need project overview or health check
  • Preparing status updates
  • Planning sprints or releases
  • Making schedule/scope decisions
  • Coordinating across workstreams

Release Engineer - Invoke when:

  • Preparing for deployment
  • Creating deployment documentation
  • Planning rollback procedures
  • Responding to production incidents
  • Conducting postmortems

QA Strategist - Invoke when:

  • Planning test strategy for features
  • Analyzing escaped defects
  • Defining or updating Definition of Done
  • Reviewing test coverage
  • Investigating flaky tests

Stakeholder Liaison - Invoke when:

  • Preparing for client meetings
  • Delivering difficult news
  • Managing conflicting expectations
  • Creating communication plans
  • Handling escalations

Hook Reference

PreToolUse Hooks

These run before a tool executes and can block or warn.

HookTriggerBehavior
check-branch.shEdit, WriteBlocks if on main/master branch
validate-commit-message.shBash (git commit)Warns if not conventional commit format
pre-release-checklist.shBash (deploy/release)Warns if deployment checklist has incomplete items

PostToolUse Hooks

These run after a tool executes and provide reminders.

HookTriggerBehavior
requirements-sync-reminder.shEdit, WriteReminds to sync REQUIREMENTS-INDEX.md

Stop Hooks

These run when a session ends.

HookBehavior
session-summary-reminder.shPrompts for session documentation if commits were made
risk-review-reminder.shLists risks not reviewed in 2+ weeks
sprint-completion-check.shReminds about sprint review if sprint end date passed

Hook Configuration

Hooks are configured in .claude/settings.json:


{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit",
        "hooks": [{"type": "command", "command": ".claude/hooks/check-branch.sh"}]
      },
      {
        "matcher": "Write",
        "hooks": [{"type": "command", "command": ".claude/hooks/check-branch.sh"}]
      },
      {
        "matcher": "Bash",
        "hooks": [
          {"type": "command", "command": ".claude/hooks/validate-commit-message.sh"},
          {"type": "command", "command": ".claude/hooks/pre-release-checklist.sh"}
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit",
        "hooks": [{"type": "command", "command": ".claude/hooks/requirements-sync-reminder.sh"}]
      },
      {
        "matcher": "Write",
        "hooks": [{"type": "command", "command": ".claude/hooks/requirements-sync-reminder.sh"}]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {"type": "command", "command": ".claude/hooks/session-summary-reminder.sh"},
          {"type": "command", "command": ".claude/hooks/risk-review-reminder.sh"},
          {"type": "command", "command": ".claude/hooks/sprint-completion-check.sh"}
        ]
      }
    ]
  }
}

Integration Patterns

Vision → Spec → Requirements Flow


1. /spec vision                 Creates vision.md (optional)
2. /spec create                 Creates product-spec.md with CAP-01, CAP-02, etc.
3. /spec approve                Approves spec, enables requirement creation
4. /requirement propose         Creates REQ-0001 as candidate, links to CAP-01
5. /requirement approve REQ-0001  Approves for implementation
6. /requirement create REQ-0001   Adds detailed acceptance criteria

Requirements → Sprint Flow


1. /requirement create REQ-0001 Creates detailed requirement (status: active)
2. /solution create             Creates SOL-0001, links to REQ-0001
3. /backlog add                 Adds REQ-0001 to backlog
4. /sprint start                Pulls REQ-0001 into SPRINT-01
5. /sprint complete REQ-0001    Marks complete
6. Update traceability matrix   CAP-01 → REQ-0001 → SOL-0001 → SPRINT-01

Risk → Mitigation Flow


1. /risk create                 Creates RISK-0001
2. /risk assess                 Full risk assessment session
3. /risk matrix                 Visualize priorities
4. Work on mitigation           Update RISK-0001 with progress
5. /risk update RISK-0001       Reassess, possibly close

Change Request Flow


1. /change create               Creates CR-0001 with impact analysis
2. Review impact                Schedule, effort, scope, cost
3. /change approve CR-0001      Record approval
4. Update sprint                Add work to current or next sprint
5. /change implement CR-0001    Track implementation

Release Flow


1. /release plan                Creates REL-1.0.0
2. /release prepare             Verify completeness
3. /release checklist           Creates DEPLOY-REL-1.0.0
4. Walk through checklist       Pre-deployment verification
5. /release deploy              Execute deployment
6. Monitor                      Watch for issues
7. (if issues) /release rollback Execute rollback, create incident

Incident Response Flow


1. Incident detected            Alert or user report
2. Triage and assess severity   S1-Critical to S4-Minor
3. Investigate and mitigate     Fix or workaround
4. Create postmortem            INC-0001 with timeline, root cause
5. Create action items          Prevent recurrence
6. /risk create                 If pattern indicates systemic risk

Best Practices

General

  1. Start small - Use only what you need; add more as complexity grows
  2. Be consistent - Use the same patterns and conventions throughout
  3. Keep it current - Stale documentation is worse than no documentation
  4. Link entities - Cross-reference related items for traceability
  5. Review regularly - Risks, backlog, and status should be reviewed weekly

Requirements

  • Write acceptance criteria that are specific and testable
  • One requirement per user-visible capability
  • Keep requirements independent when possible
  • Use the requirements-analyst agent for complex requirements

Sprints

  • Don't overcommit (80% capacity rule)
  • Have a clear, achievable sprint goal
  • Track daily progress, not just end-of-sprint
  • Always do retrospectives - they're where improvement comes from

Risks

  • Identify risks early - they're cheaper to mitigate
  • Review risks at least bi-weekly
  • Close risks that are no longer relevant
  • Create new risks when patterns emerge

Releases

  • Never skip the checklist
  • Always have a rollback plan
  • Deploy when you can monitor (not Fridays)
  • Communicate before, during, and after

Communication

  • No surprises for stakeholders
  • Bad news travels best when delivered early
  • Tailor communication to the audience
  • Document decisions in journal

Appendix: Risk-Appropriate Usage

Not every project needs every feature. Use this guide:

Zero-Risk Projects (bodmail, iwpi-lab)

Required:

  • Basic requirements tracking (/requirement)
  • Session summaries (/session-summary)

Optional:

  • Everything else - use what helps learning

Medium-Risk Projects (peabod-www)

Required:

  • Requirements tracking (/requirement, /solution)
  • Sprint management (/sprint, /backlog)
  • Basic status reporting (/status quick)
  • Release management (/release)

Recommended:

  • Risk management (/risk)
  • Change control (/change)

High-Risk Projects (nanawall)

Required:

  • Full requirements tracking
  • Sprint management with retrospectives
  • Comprehensive status reporting
  • Full release management with checklists
  • Risk management
  • Change control
  • Stakeholder communication plan

Recommended:

  • Incident management procedures
  • Quality metrics tracking
  • Regular traceability matrix updates
